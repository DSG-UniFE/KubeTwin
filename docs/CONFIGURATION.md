# Writing a KubeTwin configuration file

A `.conf` file (see `examples/*.conf`) is not a data format — it's a Ruby
script that gets `instance_eval`'d against a `Configuration` object
(`Configuration.load_from_file`, [`lib/kube_twin/configuration.rb`](../lib/kube_twin/configuration.rb)).
Every top-level directive (`start_time`, `federation`, `microservice_types`, ...)
is a method generated by `dsl_accessor`
([`lib/kube_twin/support/dsl_helper.rb`](../lib/kube_twin/support/dsl_helper.rb)):

```ruby
def key(*val)
  val.empty? ? @key : (@key = val.size == 1 ? val[0] : val)
end
```

Calling `key <value>` sets it; calling `key` with no arguments reads it back.
Because it's plain Ruby, you can use local variables (`seed = 12345`, then
reuse `seed:` inside later blocks), `require`, string interpolation, loops,
etc. — see `examples/test.conf` for a file that does `require 'json'` and
builds part of its config programmatically.

This document only covers directives that are actually read back by the
simulator (verified against `lib/`, not just inferred from examples). A few
DSL keys exist but are dead — see [Unused/legacy keys](#unusedlegacy-keys)
at the bottom.

## Minimal skeleton

```ruby
start_time DateTime.civil(2020, 5, 28, 0, 0, 0).to_time
warmup_duration 10.seconds
cooldown_duration 10.seconds
duration 10_000.seconds
stats_print_interval 1
seed 12345

federation \
'{
  "resources": { "cluster1": { "cpu": "4000", "mem": "8000" } },
  "latencies": []
}'

customers \
  1 => { location_id: 0 }

workflow_types \
  1 => { component_sequence: [ { name: "my_service" } ] }

request_gen \
  1 => {
    workflow_types: 1,
    starting_time: start_time,
    request_distribution: { distribution: :exponential, args: { rate: 10, seed: seed } },
    num_requests: 1000,
    num_customers: 1
  }

microservice_types \
  "my_service" => {
    service_time_distribution: {
      mec:   { distribution: :gaussian, args: { mean: 0.01, sd: 0.002, seed: seed } },
      cloud: { distribution: :gaussian, args: { mean: 0.05, sd: 0.006, seed: seed } }
    },
    resources_requirements_cpu: 200,
    resources_requirements_memory: 40,
    node_affinity: "local",
    rps: 100
  }

services \
  'my_service' => { serviceName: 'my_service', selector: 'my_service' }

replica_sets \
  'app1' => { name: 'app1', selector: 'my_service', replicas: 1 }
```

Run it with `bundle exec bin/kube_twin examples/your.conf`.

## 1. Simulation clock

| Directive | Type | Notes |
|---|---|---|
| `start_time` | anything responding to `.to_f` | Examples use `DateTime.civil(y,m,d,h,mi,s).to_time`; internally coerced with `.to_f`, i.e. treated as a Unix timestamp. |
| `duration` | `Integer#seconds` (from the `as-duration` gem) or plain number | Total simulated time. |
| `warmup_duration` / `cooldown_duration` | same as above | Stats collected during warmup/cooldown are excluded from the final report. `cooldown_duration` defaults to `10` if omitted. |
| `stats_print_interval` | number (seconds) | How often running stats are printed while the sim executes. |
| `seed` | integer | Not read by the framework itself — it's just a plain Ruby local/method you're expected to reuse as `seed: seed` inside distribution `args:` so every random source in the file shares one seed. |

**`seeds` — known footgun.** You'll see this idiom in several examples:

```ruby
seeds \
  {communication_latencies 12345}
```

This looks like it sets a hash, but it doesn't. Since `seeds` is a
zero/one-arg method, a `{ ... }` immediately following a bare `seeds` call is
parsed by Ruby as a **block**, not a hash argument — and the generated
`dsl_accessor` method never `yield`s, so the block body never even runs.
`Configuration#validate` then quietly defaults `@seeds` to `{}}` when it was
never set, so **this syntax silently does nothing** (verified: it evaluates
to `{}`/`nil`, not `{communication_latencies: 12345}`). If you actually want
to seed the communication-latency RNG separately from the request-generation
RNG, use one of these instead:

```ruby
seeds communication_latencies: 12345
# or
seeds({ communication_latencies: 12345 })
```

## 2. Infrastructure topology: `federation` vs `clusters`+`latency_models`

These are two intentionally different, supported topology models, not an
old-vs-new pair. `federation` is a simplified, JSON-based description meant
to be generated/consumed by the Optimuum framework, which KubeTwin
integrates with — it trades expressiveness for being easy to produce
programmatically from Optimuum's own cluster/latency model. `clusters` +
`latency_models` is the lower-level, more detailed way to describe an
arbitrary set of clusters and the latency between every pair of them, and
is what you'd reach for when hand-writing a topology or when you need
per-cluster `type`/`tier` control that `federation` can't express.

**They are not additive** — `lib/kube_twin/ksimulation.rb` checks
`federation.nil?` at every call site: if `federation` is set, `clusters` and
`latency_models` are silently ignored even if also present in the file
(this is the exact situation in `examples/test.conf`, which defines both —
`federation` wins there, since it's the format an Optimuum-driven run would
supply).

### `federation` (JSON string)

```ruby
federation \
'{
  "resources": {
    "cluster1": {
      "cpu": "7000", "mem": "4096", "num_nodes": 1,
      "nodes": [ { "node": "cluster1", "cpu": "7000", "mem": "4096" } ]
    },
    "cluster2edge": { "cpu": "7000", "mem": "8192" }
  },
  "latencies": [
    { "src": "cluster1", "dst": "cluster2edge", "value": "0.030" }
  ]
}'
```

- Every entry under `resources` becomes one `Cluster`. Note it's a **quoted
  Ruby string** containing JSON, not a Ruby hash.
- `nodes` is optional; if omitted, node count defaults to
  `cpu / 4000` (one node per 4000 mCPU) and per-node cpu/mem is the
  aggregate split evenly (nodes are assumed homogeneous).
- All `federation` clusters are created with `type: :mec, tier: 'local'`
  hardcoded — you cannot express a `:cloud` cluster or a different `tier`
  through `federation`; use `clusters` (below) if you need that.
- `latencies` entries: `src`/`dst` are resource names from `resources`,
  `value` is treated as a **round-trip** time in seconds and halved
  internally to a one-way latency, then perturbed with Gaussian jitter
  (mean 0, sd 10 ms, clamped ≥1 ms). Pairs not listed fall back to routing
  through location 0. Same-cluster latency uses its own fixed
  Gaussian(5 ms, 1 ms).
- An empty `"latencies": []` is valid (single-cluster setups, e.g.
  `examples/parallel-working-test.conf`).

### `clusters` + `latency_models`

The older, more verbose model, still fully supported:

```ruby
clusters \
  one: {
    name: "cluster1",
    location_id: 1,
    type: :mec,           # :mec or :cloud — anything else raises
    tier: "local",        # free-form string, matched against microservice_types[...][:node_affinity]
    node_number: 1,
    node_resources_cpu: 8000,
    node_resources_memory: 8000,
  }

latency_models \
  [
    # row for location_id 0: [ (0,0), (0,1), (0,2), ... ]
    [
      { distribution: :gaussian, args: { mean: 0.003, sd: 0.0014 } },
      { distribution: :mixture, args: ERV::GaussianMixtureHelper.RawParametersToMixtureArgs(
          33, 9.24e-6, 1.69e-6,  33, 10.87e-6, 1.73e-6,  33, 11.19e-6, 1.40e-6) },
    ],
    # row for location_id 1: [ (1,1), (1,2), ... ]  -- only entries for j >= i
    [
      { distribution: :gaussian, args: { mean: 0.0126, sd: 0.00582 } },
    ],
  ]
```

- `latency_models` is a **compact upper-triangular matrix**: row `i`
  contains only the distributions for pairs `(i, i)`, `(i, i+1)`, `(i, i+2)`,
  ... in that order — not a full `N×N` matrix. Location `0` is conventionally
  the end-user.
- Each cell is any `ERV::RandomVariable` spec (`distribution:` + `args:`),
  same as everywhere else in the DSL — a plain distribution, or a
  `:mixture` built from raw Gaussian-mixture parameters via
  `ERV::GaussianMixtureHelper.RawParametersToMixtureArgs(weight, mean, sd, ...)`.
- `type:` is functionally significant (`:mec`/`:cloud` select which half of
  a microservice's `service_time_distribution` applies); `tier:` is only
  meaningful in that it must textually match a microservice's
  `node_affinity` for the scheduler to prefer that cluster.

## 3. `customers`

```ruby
customers \
  1 => { location_id: 0 }
```

One entry per customer id, only field is `location_id` (index into
`clusters`/`federation` locations, used for latency sampling and to key
per-customer stats).

## 4. `workflow_types`

```ruby
workflow_types \
  1 => {
    component_sequence: [
      {
        name: "productpage",
        calls: [
          { name: "details" },
          { name: "reviews", calls: [ { name: "ratings" } ] }
        ]
      }
    ]
  }
```

- `component_sequence` is the ordered list of top-level steps of the
  workflow. A flat list with no `calls:` at all also works (see
  `examples/test.conf`'s two-step `my_solver`/`georef_module` workflow) —
  it just means none of the components call each other synchronously.
- `calls:` nests further requests dispatched *by* that component (e.g.
  `productpage` calling `details`, which is how a microservice chain /
  fan-out is expressed), and can recurse arbitrarily deep.
- A **parallel** step branches execution instead of nesting it:

  ```ruby
  { type: "parallel", branches: [ { name: "reviews" }, { name: "details" } ], wait_for: "all" }
  ```

  see `examples/parallel-working-test.conf`. Each entry in `branches` is
  itself a `component_sequence`-style step (so branches can have their own
  `calls:` too), dispatched concurrently as cloned requests; the parent
  request proceeds to the step after the parallel block once the branches
  complete.

## 5. Request generation

Two mutually exclusive mechanisms; if `request_gen` is set (non-nil), it
always wins over `request_generation`, even if both are present in the file
(as in `examples/example-hpa.conf`).

### `request_gen` — synthetic traffic

```ruby
request_gen \
  1 => {
    workflow_types: 1,               # sample a workflow id uniformly in 1..N
    starting_time: start_time,
    request_distribution: { distribution: :exponential, args: { rate: 30, seed: seed } },
    num_requests: 10_000,
    num_customers: 1                 # sample a customer id uniformly in 1..N
  }
```

You can define multiple numbered entries (`1 => {...}, 2 => {...}`) to layer
several traffic phases with different start times/rates/workflows in the
same run. `request_distribution` accepts any `ERV::RandomVariable` spec, not
just `:exponential`. `workflow_types`/`num_customers` must therefore be
contiguous `1..N` ranges of ids that exist in your `workflow_types`/
`customers` hashes.

### `request_generation` — replay from a file

```ruby
request_generation \
  { filename: '<pwd>/requests.csv' }
```

Only used when `request_gen` is absent. Reads a CSV (header row skipped),
using only column 0 as the arrival time — workflow type and customer id are
both hardcoded to `1`. The literal token `<pwd>` in any string value is
substituted with the config file's own directory, so paths can be written
relative to the `.conf` file regardless of the current working directory.

## 6. `microservice_types`

```ruby
microservice_types \
  "productpage" => {
    service_time_distribution: {
      mec:   { distribution: :lognorm, args: { mu: -3.9863, sigma: 0.4237, seed: seed } },
      cloud: { distribution: :lognorm, args: { mu: -3.9863, sigma: 0.4237, seed: seed } }
    },
    resources_requirements_cpu: 200,
    resources_requirements_memory: 40,
    node_affinity: "local",
    mdn_file: "./mdn_models/productpage_weights.json",
    rps: 100,
    rps_correction_factor: 1.6,
    wait_for: ["details"],
  }
```

The hash key (`"productpage"`) is the component name referenced from
`workflow_types.component_sequence[].name`, `services[].selector` and
`replica_sets[].selector` — all four must use the exact same string.

| Field | Meaning |
|---|---|
| `service_time_distribution` | `{mec: {...}, cloud: {...}}`, picked by the *cluster type* the pod lands on. **Only used when `mdn_file` is not set** — with `mdn_file` present, service time comes from the model instead. |
| `mdn_file` | Path to a `*_weights.json` exported by the MDN training pipeline (see [`mdn_models/README.md`](../mdn_models/README.md) and the [torch-rb install instructions](../README.md#installing-torch-rb-libtorch)). Loaded once per microservice type; if set, it takes over service-time sampling entirely, driven by the live RPS (below). |
| `rps` | Static requests-per-second fed to the MDN as its input feature. |
| `rps_correction_factor` | Multiplier applied to the (live or static) RPS before it reaches the MDN. Default 1.0. |
| `use_configured_rps` | If `true`, always use the static `rps` value. If unset/`false`, RPS is instead computed live from a 10-second sliding window of recent arrivals, falling back to the static `rps` if too few samples exist. |
| `resources_requirements_cpu` / `_memory` | Per-pod resource request, used by the scheduler for bin-packing. |
| `node_affinity` | A `tier` string (`"local"`, `"t1"`, `"t2"`, `"rdc"`, ...) — the scheduler prefers a node whose cluster `tier` matches; otherwise falls back to the least-loaded node. |
| `wait_for` | Array of other microservice-type names this one depends on. When this component's step completes, an upstream caller that's registered as waiting on it is only released once every name in `wait_for` has responded — use it to model a request that isn't "done" until a dependency also replies. |

## 7. `services` and `replica_sets`

```ruby
services \
  'productpage' => { serviceName: 'productpage', selector: 'productpage' }

replica_sets \
  'app1' => { name: 'app1', selector: 'productpage', replicas: 1 }
```

- `services` registers a DNS-style entry keyed by **`selector`**, not by the
  hash key or `serviceName` — `serviceName` is cosmetic. Workflow component
  lookups resolve by this `selector`, so it must equal the component name
  used everywhere else (`microservice_types` key, `component_sequence.name`,
  `replica_sets.selector`).
- `replica_sets.replicas` is only the **initial** pod count — it's mutable
  at runtime by a Horizontal Pod Autoscaler (below) or by an external
  allocation/optimizer step.

## 8. `horizontal_pod_autoscalers` (optional)

```ruby
horizontal_pod_autoscalers \
  1 => {
    name: 'productpage',              # must match a replica_sets/services selector
    minReplicas: 1,
    maxReplicas: 5,
    targetProcessingPercentage: 0.7,
    periodSeconds: 15,
  }
```

Every `periodSeconds`, the controller compares current vs. desired load
(`targetProcessingPercentage * observed service time`); if the ratio falls
outside `0.90..1.10` it scales the matching `replica_sets` entry up or down,
bounded by `minReplicas`/`maxReplicas`. See `examples/example-hpa.conf`.

## 9. `evaluation`

```ruby
evaluation \
  cluster_hourly_cost: [
    { cluster: :cloud_control_plane, fixed_cpu_hourly_cost: 0.080, fixed_memory_hourly_cost: 0.070 },
    { cluster: :rome, fixed_cpu_hourly_cost: 0.100, fixed_memory_hourly_cost: 0.100 },
  ],
  penalties: lambda { |general_stats, per_workflow_and_customer_stats|
    500.0 if general_stats.mean > 0.500
  }
```

- `cluster_hourly_cost` entries are matched to clusters **by array position**,
  not by the `cluster:` label — list them in the same order you declared
  `clusters`/`federation.resources`. The `cluster:` key itself is only used
  by `Evaluator#evaluate_fixed_costs_*` (`lib/kube_twin/evaluation.rb`),
  which isn't called from the main simulation loop today.
- `penalties` is accepted and stored but **its call site is currently
  commented out** in `lib/kube_twin/evaluation.rb` — it has no effect on the
  simulation output even though every example defines one. Left in place
  for forward-compatibility / scripts that construct an `Evaluator`
  directly.
- The number printed as `Weighted sum` / `Result` at the end of a run is
  computed in `KUBETWIN::KSimulation` from: mean response time, a
  Gini-based replica-spreading penalty, per-microservice and per-chain
  latency-threshold penalties (see `policies` below), and an availability
  penalty — **not** from `evaluation.penalties`.
- `custom_stats` (a sibling top-level directive, not nested under
  `evaluation`) can seed extra `longer_than` thresholds per
  workflow/customer pair:

  ```ruby
  custom_stats \
    [ { workflow_type_id: 1, customer_id: 1, longer_than: [0.1, 0.2] } ]
  ```

## 10. `policies`

```ruby
policies [
  {
    type: 'torch.policies.Placement.ServiceChainResponseTime',
    properties: { service_chain_max_latency_ms: 3000 },
    chains: ['productpage', 'reviews', 'ratings'],
    targets: []
  },
  {
    type: 'torch.policies.ApplicationService.Performance.Availability',
    properties: { target_availability_percentage: 99.999 },
    targets: []
  }
]
```

**`type:` is documentation only — the simulator never dispatches on it.**
Only `properties` and `chains`/`targets` are actually read, and the
behaviour is selected purely by *which properties key is present*:

| `properties` key | `chains` or `targets` | Effect |
|---|---|---|
| `service_chain_max_latency_ms` | `chains: [component names, in order]` | Adds a latency SLO to that specific call chain (must be a subset of an existing workflow's components, or the sim raises `Chain not found in available workflows`). |
| `target_availability_percentage` | — | Sets the availability threshold used in the final penalty calculation. |
| `latency_max_value_ms` / `response_time_value_ms` | `targets: [microservice names]` | Adds a per-component latency SLO (both keys behave identically today). |

## Unused/legacy keys

These are declared as DSL accessors and get deep-frozen by
`Configuration#validate`, but nothing in `lib/` ever reads them back — safe
to ignore when writing a new config: `constraints`, `data_centers`,
`kpi_customization`, `node`.
